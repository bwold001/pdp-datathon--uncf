# ADR 0001 Shared analysis boundary for Student Success Chat v2

Date: November 10, 2026. Status: implementation direction for issues #45–#57; recorded by Task 0 (#46). This ADR does not claim the v2 code or release gates are implemented.

## Context

Dashboard measures/page breakdowns live in `measures/`. Graduation, entry-program retention, annual enrollment and their receipts live in `analytics/`. They have different disclosure and eligibility rules. A common function cannot ensure parity when callers read different source generations. Existing v1 chat already proposes, clarifies and confirms scopes before deterministic execution, but only supports three analyses and one unresolved request.

The verified checkout is `8407844177c87326b98dcd642c57c04eeece1a5b`; see [baseline inventory](../chat-v2-baseline.md) for exact owners, denominators, test evidence and documented mismatches.

## Decision

1. Add one typed orchestration facade in `analytics/analysis_service.py`. Defined calculations remain in `measures/`; legacy analyses remain in their current owners; fixed exploration lives under `analytics/exploration/`. The facade contains no formulas, provider calls or HTTP imports. Registry IDs reference executable requests, definitions, versions and profiles. Do not activate arbitrary SQL/Python tools.
2. Keep cohort gateway completion and course outcomes separate. Cohort C means >=1.0/pass; course outcomes use first attempts and >=2.0/P, with a course-taker denominator. Required non-attempters recorded D affect only cohort completion. A changed cohort threshold needs verified normalized grade and attempt evidence; completion flags alone are insufficient. Preserve the unknown-requirement SQL mismatch as current behavior pending a separate decision.
3. Extract versioned `dashboard_v1`, `legacy_analytics_v1` and `exploration_v1` disclosure implementations. Registry selects the policy; models cannot choose. Dashboard/v1 adapters preserve existing visibility, units and statuses. Exploration additionally stages the complete plan and withholds linked or uncertain-overlap exploratory evidence that could recover hidden values. Preserve the known dashboard-only complementary-disclosure limitation. The new protection boundary is one returned v2 plan, not conversation history or unlimited repeated queries. Synthetic demonstration only.
4. Own a single read-only execution snapshot for all steps in an executable plan, including legacy adapters. Reuse the existing transactional loader boundary and runtime cancellation behavior. Supply tested named/positional cursors without changing a global row factory mid-plan. Snapshot identity includes source manifest, load generation, pipeline/model version and transformation digests. Legacy file-mtime/source stamps are migration inputs, not authoritative v2 identity.
5. A stable computation fingerprint includes canonical request, snapshot, operation/feature/method/implementation/configuration/coverage/profile versions, and sibling context that affects disclosure. Exclude execution IDs, timestamps and duration. Separate execution identity from reproducibility identity. Replay refuses missing snapshots or required versions instead of silently substituting current ones; there is no new archive in this work.
6. Represent incomplete scopes as typed `ProposedPlan`, then deterministically convert a fully resolved plan to immutable canonical `ExecutablePlan`. Show the entire executable scope for confirmation and revalidate its references on submission. Clarification retains every step; it is distinct from confirmation. Only executable plans calculate, including provider-free HTTP callers; no second model call is required to execute a confirmed plan.
7. Validate at most four steps, supported dependencies, acyclic order and all constraints before execution. Distinguish completed receipts (including unavailable/suppressed evidence) from failures/unexecuted steps. Report complete/partial/failed outcomes. A database interruption stops remaining execution and completes rollback/close; never reopen another snapshot to continue. Apply plan-wide disclosure to preserved completed receipts before returning them.
8. Release A includes defined/legacy adapters only and has its own gate (#53), flags, backend evidence, deployment stamp verification, prompt evaluation and tested rollback. Release B adds only the exploration operations that pass their semantics, arithmetic, limits, disclosure and mixed-plan gates (#57). Gateway variants stay unavailable until evidence supports them.

## Consequences and checks

V1 public contracts remain unchanged; add v2 contracts and explicit transport dispatch. Preserve `/results` and `/measures/{measure}`. No raw CSV/generated dictionary edits, warehouse migration, new agent framework, causal claims or regression models are authorized. Existing supported equity-gap searches remain with the gap finder.

Parity tests compare the same snapshot and canonical request across service/API/chat/CSV where applicable. Independent arithmetic tests prevent shared mistakes from passing parity. Hidden result checks inspect serialized numerical evidence and explanatory text, not only internal flags. PostgreSQL support remains unverified without integration evidence. Exact current/proposed differences and future acceptance behavior are kept in the linked baseline and [acceptance matrix](../chat-v2-acceptance.md).
